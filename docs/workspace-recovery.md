# Fictional brokerage recovery rehearsal

Run `npm run build:cloudflare` and then `node scripts/workspace-recovery.mjs`. The script boots the built Orbit Worker on loopback with two generated brokerages, synthetic staff sessions, and mock integrations. It uses an automatically created temporary directory and removes it after the run. It never takes a database path or a credential.

## What the rehearsal verifies

1. The LO changes a borrower document deadline. The loan, history, and open work reflect the edit. The assigned processor has access. Another LO in the same brokerage cannot open the file.
2. Stop the local runtime and use SQLite's online backup API to copy the target brokerage store. Check integrity, foreign keys, and fixture identity. Reject the same snapshot as a restore source for the other brokerage.
3. Save a checkpoint, an acknowledged checklist change, a stale rejected edit, and an edit interrupted before receipt acknowledgment in a separate SQLite journal. Reopen the journal and Worker. Verify that the pending receipt blocks replay and reconcile it against the exact revision and fields on the source file.
4. Revoke a borrower link, replace a realtor link, revoke a staff membership, and record a separate edit at the second brokerage. Delete the target fictional loan, verify it is unavailable, and reset the source scenario to retire its remaining active links.
5. Stop the runtime and copy its current storage to staging. Replace only the target brokerage's SQLite file in staging. This keeps the current staff directory and the second brokerage's changes. The journal stays outside both copies.
6. Recreate the older document ID with populated file metadata and omit its due-date index. Force a startup failure during the document-ID upgrade. Verify the old request, metadata, and missing index survive the failed transaction, and verify the other brokerage can still open its file. Remove the injected fault and restart.
7. Confirm the restored tenant still holds the old links but the public endpoints reject them using the current directory. Reconcile the loan and realtor records on loopback. Verify the revoked staff member remains blocked, cross-brokerage reads fail, and the other brokerage's links still work.
8. Compare the restored document deadline, history, task queue, funding figures, and processor access with the snapshot. Verify that the first CRM batch receipt and the assigned callback retain their IDs and deadline. Retry the first batch, verify that its receipt count stays the same, and commit the second batch.
9. Read only the target brokerage's post-checkpoint receipts. Replay the two verified checklist changes, restart, and replay them again. Confirm each edit appears once in history at its expected revision. The stale rejected edit never appears.
10. Restore a separate linked MISMO draft with two accepted document revisions, the prior and current manual receipts, clearance, and the original document and lender sign-offs. Export the handoff again and check that its review reference matches the pre-backup report. The reference identifies the source coverage and recorded reviews at export time. It stays stable across repeated downloads of that state.
11. Compare the restored lender evidence with the acknowledgment in the external journal before recording the later sign-off as a fresh admin review. Repeat after restart and confirm the review is recorded once. Reopen the condition and verify the former review is stale and the journaled sign-off cannot be carried forward against different evidence.

## Operating boundary

The local rehearsal uses a stopped runtime and the [Node SQLite backup API](https://nodejs.org/api/sqlite.html). Although the installed local runtime returns bookmark values, that does not prove supported hosted PITR semantics. The separate hosted procedure exercises [Cloudflare's bookmark API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#pitr-point-in-time-recovery-api).

Hosted pilot actions record explicit borrower and realtor revocations, realtor replacements, and active links retired by pilot reset as token hashes in the existing brokerage directory before acknowledging the change. The directory rejects those links through their original expiration, including when the tenant database contains an older copy. A reset protects up to 100 active links in one batch. If a link changes while reset is in progress, retry the reset. Links already protected during that attempt stay blocked. Earlier releases' revocations, ordinary record deletions, and directory recovery require separate reconciliation. Keep tenant access blocked through replay and verification.

The external checklist journal is local and limited to synthetic fixture writes. An unresolved write blocks replay until it can be reconciled against the source. The interrupted-upgrade check covers one populated schema transition. Hosted checklist journaling, uploaded document bytes, broader schema compatibility, hosted recovery time, and real-data admission have separate gates.

## Hosted rehearsal implementation boundary (November 10)

The current Cloudflare reference confirms that PITR is unavailable in local development. `getCurrentBookmark()` captures the object history point; `onNextSessionRestoreBookmark(bookmark)` schedules restoration for the next object session and returns a recovery-undo bookmark. The restore requires an object restart, normally `ctx.abort()`. These semantics must be exercised remotely; a stopped local SQLite copy cannot prove them. Reference: https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#pitr-point-in-time-recovery-api

The next rehearsal should wrap the **built OrbitWorkspace**, not a toy counter, in a separate short-lived Worker with its own SQLite namespace and document bucket. Generate its configuration from an explicit allowlist; do not copy production variables, lender credentials, routes, service bindings, or document bucket names. Only fixed fictional fixture operations should be reachable behind a short-lived operator token. The harness must never accept a production namespace, arbitrary SQL, arbitrary staff identity, or an arbitrary restore bookmark.

Required evidence before calling this gate complete:

1. Seed two generated fictional brokerages and the separate directory using real Orbit initialization and pilot workflows. Record built-source provenance, object identity and checkpoint in the directory, outside the restored tenant.
2. Capture source loan, task, document metadata, accepted revisions and history. Store and hash sample document bytes separately; database PITR does not restore R2 bytes.
3. Change the target and the other brokerage after the checkpoint. Revoke target staff and borrower/realtor links in the current directory. Persist an acknowledged operation journal outside the target tenant.
4. Reject a checkpoint belonging to another tenant. Close the target to normal traffic, preserve the undo bookmark durably, then restart only its object. Treat the expected abort response as inconclusive until the next session verifies the checkpoint and source identity.
5. Verify source records against the checkpoint, the other brokerage against its newer state, and continued rejection of revoked identities and tokens through the normal routing checks. Reconcile document object IDs to readable bytes and hashes; missing or mismatched bytes must prevent reopening.
6. Reconcile/replay only acknowledged post-checkpoint edits with original revision and idempotency evidence. Repeated replay must not duplicate tasks or history. Record timings, failures, and the recovery decision before reopening.
7. Retain sanitized evidence and remove the isolated worker/bucket after verification. A successful isolated run still does not certify production directory recovery, retention policy, disaster response staffing, or real-data admission.

### First hosted result (November 11)

The isolated Worker `orbit-recovery-1aca0c5b` restored a real built OrbitWorkspace using Cloudflare's bookmark and object restart. The target matched its checkpoint across five loans, three tasks, four applications, one document request and one file metadata row. The second fictional brokerage retained its later change. Borrower and staff revocations remained effective through normal application routing. Cross-tenant checkpoint and write attempts were rejected, the sample R2 bytes matched their recorded hash, and an undo bookmark was retained outside the restored tenant. Restore plus verification took 1,161 ms for this fixture; this is not a production recovery-time commitment.

The harness provenance was `629f3a2802c639063d7a4d5476ef49a04f3e8514`; the application build came from `e267adf` (the intervening change only corrected a harness expectation). The cleanup wrapper was updated after verification. The fixture object, isolated Worker and dedicated R2 bucket were deleted after retaining [sanitized evidence](evidence/hosted-recovery-2026-11-11.json). Source lint passed after generated rehearsal copies were excluded from linting.

This establishes the core hosted restore, isolation and document-byte check. It does **not** complete R4: this first fixture had no loan audit rows, did not exercise accepted document revisions or realtor revocation, and did not replay acknowledged later edits. Missing/corrupt-byte rejection, operator maintenance controls, production directory recovery and real-data admission remain separate gates. No production tenant was restored or altered by this rehearsal.

### Hosted replay and negative checks (November 11)

The second isolated run used source/build `401d510a6b13860d9b4f83e200b13cb432f756ed`, with an SHA-256 recorded over the copied application and wrapper modules. Remaining recovery acceptance: accepted document revision and lender receipt history; nonempty loan audit coverage; interrupted/ambiguous acknowledgment reconciliation; production operator maintenance and reopening controls; and directory recovery. The hosted receipt journal is still a test harness, not a shipped general write journal or an operator recovery UI. R4 and real-data admission remain open.

### Historical accepted PDF bytes (November 11 candidate)

The byte-level extension found a product gap: replacement retained acceptance metadata but could enqueue the prior PDF for deletion. Candidate `e84ea381245c6e61667ddae5c1bd50536b3335ac` retains the object identity, upload time and mode alongside each accepted revision. Cleanup respects those references and releases objects when their last retaining request is removed. Existing installations backfill only a currently accepted revision whose PDF can be proved from current metadata; older missing associations remain unavailable.

The isolated hosted Worker `orbit-recovery-20d18d6a` uploaded two distinct built-in PDFs through the normal mock verification/upload endpoints, accepted each, recorded both manual lender receipts and clearance, then checkpointed the actual application. After deleting and restoring the loan, both retained object references and both original SHA-256 hashes matched. Missing and corrupt bytes were rejected for each revision. Prior isolation, revocation, audit and repeated receipt replay checks passed again. Restore and initial verification took 2,710 ms for this fictional fixture. [Sanitized evidence](evidence/hosted-recovery-pdf-bytes-2026-11-11.json) records the source, artifact hash and two retained PDFs.

Both fixture PDFs, the dedicated Worker and bucket were removed after verification. This is candidate recovery evidence, not a production deployment or recovery certification. Ambiguous acknowledgment reconciliation, operator maintenance/reopening controls, directory recovery and a production retention policy remain open.
