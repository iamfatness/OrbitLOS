## Required complete flow

1. Checkpoint impact index: each application SQL row gets stable primary-key/rowid identity and content hashes; minimal root record IDs/names identify loans, contacts, referral leads, campaigns. Resolve known direct/indirect associations; report unlinked changes explicitly. Keep all raw row content, answers, credentials and bookmark values out of HTTP. Old checkpoints still support table comparison; detailed index is unavailable for older points. Chunk impact index in directory to stay below SQLite single-value limits. Paginate affected records25 at a time.
2. Checkpoint external-document evidence: collect all non-null object IDs from current, accepted, linked condition evidence, lead and lender package references; read/hash bounded R2 bytes for a new checkpoint. Preserve unavailable associations as baseline limitations; non-null missing/corrupt required files block restore. Do not restore/delete external bytes. Detect pending uploads and refuse restore. Directory grants/routes/revocations remain untouched and must be reviewed independently.
3. Restore preview: paused pilot admin only, current revision; exact selected checkpoint; compare current SQL/KV and required external-file evidence. Show record impact, baseline file limitations, and blockers. Older point lacking necessary evidence, schema mismatch, changed protected UWM credential/operation evidence, pending uploads or pending internal replay block execution. No real lender retry. A fingerprint binds preview to actual current state and selected point.
4. Persisted restore job: directory keeps target checkpoint, automatic before-restore checkpoint/bookmark, actor/note, command digest, maintenance cycle, durable state. Create source checkpoint and job atomically; invalidate reopening approval and advance revision. One pending restore per brokerage. Pending restore blocks reopen/review, new checkpoints, internal replay and other evidence mutations. Current admins may resume a job after response loss. Never expose bookmarks publicly.
5. Tenant apply: closed/drained gate; authorize job from directory; verify current state exactly equals reviewed source before arming. If target already matches, verify and finish without rearming. Call onNextSessionRestoreBookmark for the job's fixed target, record armed state/undo bookmark in directory, then ctx.abort. A lost acknowledgment leaves a pending job. The pre-restore bookmark is persisted before arming so an interrupted arm cannot lose the original recovery point.
6. Resume: inspect after restart. If target SQL/KV and required file evidence match, finish job with durable completion/history and require fresh reopening review. If source still matches, retry same target safely while paused. If neither matches, keep workspace paused with an explicit unresolved outcome; never blindly replay or declare success. Scheduler state is reported separately and normal reopening rebuilds the next alarm. Uncertain work must never reopen.
7. UI: progressively disclosed restore preview under selected checkpoint; one explicit consequential action with selected point, actual brokerage-name confirmation, reviewed-impact checks and reason. Retain form entries on failure; pending jobs have a clear resume/check-outcome control. Never disguise full restore as a per-record undo. Reopening remains a separate reviewed step.
8. Acceptance: unit tests for affected records, exact retry/stale/revoked/cross-tenant/size limits and pending gates; built-Worker full41-stage extension; local responsive/failure UX; isolated hosted actual product checkpoint->source edits->preview->restore->resume->comparison->covered replay->review/reopen, lost replies and no duplicate history. Verify PDFs and directory revocations/other tenant remain unchanged. Preserve new UWM directory routing tables. Publish full combined candidate preserving bindings/assets, verify fictional live preview/controls, update public product and roadmap/evidence. R4/R5 remain active until remaining requirements proven.
